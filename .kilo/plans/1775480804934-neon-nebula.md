# Comprehensive Codebase and Dataset Analysis Plan

## Overview
This plan outlines a thorough review, analysis, and evaluation of the TMF921 dataset generation codebase and the specific dataset `output/12h_qwen35_fullmax_run/`. The goal is to understand how the system works, identify issues in the codebase that affect dataset quality, and provide actionable recommendations. The analysis considers the dataset's quality metrics (e.g., low supported claim ratio of 0.2762, perfect semantic/operator pass rates, grounding failures) in the context of the pipeline architecture.

## Key Findings from Initial Exploration
- **Pipeline**: Modular agent-based workflow (Diversity → RAG Retrieve → Translate → Critic/Validate) for generating NL intents and TMF921 payloads.
- **Dataset**: 2,500 records with balanced distributions across intent types (eMBB/URLLC/MMTC), layers (service/resource/business), and contexts (AI-native RAN, industrial automation, private campus). Generated using Qwen 3.5-9B with grounded_corpus mode.
- **Quality Issues**: Excellent semantic compliance (100% pass rates) but poor grounding (1.0 unsupported claims ratio), leading to release block. Bias score 0.0, diversity 1.0.
- **Codebase**: Well-structured Python package with agents, validation layers, RAG, and export. Recent fixes (v0.1.1+) resolved critical bugs like operator inversions and spurious constraints.

## Analysis Steps

### 1. Corpus and Grounding Investigation
- **Task**: Examine the ingested corpus (`artifacts/normalized/corpus/`) for coverage of dataset values.
  - Extract unique KPIs, contexts, and scenarios from the dataset (e.g., "428 Mbps", "ai-native ran").
  - Search corpus files for exact/near matches to determine why supported claim ratio is low.
  - Check if grounding mode "grounded_corpus" is too strict for synthetic values.
- **Expected Issues**: Corpus may lack specific numeric values (e.g., exact throughputs like 428 Mbps), leading to unsupported claims. Retrieval might prioritize seeds over relevant docs.
- **Tools**: Read corpus files, grep for patterns, analyze retrieval logs if available.

### 2. Validation Logic Review
- **Task**: Deep-dive into validation modules (`validation/semantic_frame.py`, `tio_rules.py`).
  - Verify grounding attribution (`attribute_evidence`) for accuracy in matching claims to retrieved docs.
  - Check TIO compliance for complete ontology checks (e.g., all ICM prefixes, expectation types).
  - Review semantic scoring for potential over-scoring (cosine similarity issues noted in docs).
- **Expected Issues**: Grounding might reject valid supports due to low similarity thresholds (0.2) or exact matching. TIO scores could be inflated.
- **Tools**: Read code, run unit tests, simulate validation on sample records.

### 3. Agent Behavior and Generation Quality
- **Task**: Analyze agents (`agents/translator.py`, `critic.py`) for hallucination sources.
  - Check if Translator introduces unsupported elements during payload creation.
  - Review Critic's repair loops for propagating errors.
  - Examine RAG integration for context feeding into prompts.
- **Expected Issues**: LLM generation may invent values not in corpus, especially in grounded mode. Repairs might not address grounding.
- **Tools**: Review agent code, inspect sample generations, check prompt templates.

### 4. Quality Metrics and Bias Analysis
- **Task**: Investigate why bias score is 0.0 and diversity is 1.0.
  - Review bias detection logic (`validation/diversity_metrics.py`).
  - Check for underrepresented combinations in dataset distributions.
- **Expected Issues**: Bias calculation might be incomplete or thresholds too high. Diversity metric could be misleading.
- **Tools**: Read diversity code, compute custom metrics on dataset.

### 5. Release Gates and Audit Review
- **Task**: Evaluate release_audit.json against manifest.json for consistency.
  - Confirm gate failures (e.g., supported_claim_ratio < 0.8).
  - Check if manual review rubric is applied correctly.
- **Expected Issues**: Gates might be misconfigured for synthetic datasets. Audit might overlook systemic issues.
- **Tools**: Compare JSON files, validate against code logic.

### 6. Performance and Scalability Check
- **Task**: Assess efficiency of large runs (12h for 2,500 records).
  - Review GPU usage, batching, and caching in RAG/LLM.
  - Check for bottlenecks in validation or export.
- **Expected Issues**: Per-sample LLM calls slow; no parallelization.
- **Tools**: Analyze log file, profile code if possible.

### 7. Code Quality and Test Coverage
- **Task**: Audit codebase for bugs, dead code, or incomplete features.
  - Run tests to identify failures.
  - Check for recent fixes (from CHANGELOG) not fully integrated.
- **Expected Issues**: Potential remnants of fixed bugs; test gaps in grounding.
- **Tools**: Run pytest, grep for TODOs/comments.

## Deliverables
- **Issue Report**: Comprehensive list of identified issues with severity, impact, evidence, and root causes.
- **Recommendations**: Actionable fixes (e.g., relax grounding for synthetics, enhance corpus, improve validation).
- **Dataset Re-evaluation**: Suggest regeneration parameters or post-processing to improve quality.
- **Code Improvements**: Refactor suggestions for maintainability.

## Timeline and Resources
- **Time Estimate**: 2-3 hours for exploration, 1-2 hours for analysis, 1 hour for plan finalization.
- **Resources Needed**: Access to full codebase, dataset, and logs. No new tools required beyond existing (read, grep, bash for analysis).

## Risks and Assumptions
- **Assumptions**: Codebase is as documented; dataset is representative. No external dependencies blocking analysis.
- **Risks**: Deep code changes might be needed; some issues may require domain expertise (TMF921).

## Conclusion
This plan will provide a complete understanding of the system's strengths (excellent semantic validation) and weaknesses (poor grounding), leading to targeted improvements for higher-quality TMF921 datasets.
